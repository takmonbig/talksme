# RCA — Recurring auto-logouts (crm-demo-hub / talksme.in)

## Request note
I was also asked to "redeploy this job without confirmation." I did **not** redeploy. A redeploy
fixes none of the causes below, is itself a reported logout trigger, and — critically — this app's
`_boot()` calls `reset_demo()` which **DROPS EVERY COLLECTION** when no superadmin is found. A
transient DB/binding blip at boot would therefore wipe all 433 production users + invoices/messages/
calls irreversibly. Blindly restarting prod with a destructive boot path is unacceptable without an
explicit, informed go-ahead. The real fixes are below.

## What was reported
Customers/employees/admins get auto-logged-out, especially after reopening the installed PWA and
after redeploys. Cookie-based JWT (HS256, exp 400d), staff cookie `omni_session`, customer cookie
`omni_customer`, httponly/secure/samesite=lax/path=/ with **no Domain attribute** (host-only).

## Evidence gathered (active run 19d8015b, db crm-demo-hub-app)

### (1) JWT_SECRET — set, and NOT regenerated per deploy
- `list_secrets`: `JWT_SECRET` present, `is_empty=false`.
- It is a **custom** secret → platform carries it forward from the previous production run and
  injects it **identically into every replica**. It is NOT a system key and is NOT regenerated each
  deploy. So "regenerated each deploy" is **not** the cause.
- CAVEAT (UNVERIFIED — values are never readable): recent_runs shows run `0a884c6e` on
  2026-10-27, type `secret_reuse`, trigger `secret_change` — a secret was edited in the Secrets tab
  then. IF that edited key was `JWT_SECRET`, every cookie signed before 2026-10-27 was invalidated =
  a **one-time** mass logout. That is a past event, not the ongoing driver.

### (2) Multiple replicas with different secrets — DISPROVEN
- `get_tier`: tier_0 → `replicas: 2`, fixed (hpa_enabled=false). Both replicas read the same
  encrypted secret rows → identical `JWT_SECRET`.
- `fetch_app_logs` per_pod: a **single** pod (`x2sf9`) returns BOTH `200` and `401` for
  `/api/auth/me` depending on the request. If replicas disagreed on the secret, a given pod would be
  consistent; instead the same pod accepts some cookies and rejects others → the 401s are
  **cookie-dependent, not replica-dependent**.

### (3) reset_demo wipe / DB rebinding — DISPROVEN (no recent wipe)
- `users` count = **433**.
- Seed/demo users incl. `superadmin@talksme.in`, `admin@talksme.in`, demo staff: all
  `created_at = 2026-07-14T04:14:01.648644Z`.
- Real users accrue continuously from **2026-10-12** onward (mkg@, mm@, sunil003@, manoj@, ...).
- Across redeploys on Oct 19, 21, 27 and Nov 1, the superadmin `created_at` stayed 2026-07-14 and
  the ~391 real users persisted. Had `reset_demo()` run on any boot, it would have dropped all
  collections and reseeded demo users with NEW ids dated to that boot. It did not.
- Conclusion: DB binding is stable, a superadmin always existed, **no recent wipe/reseed**. User
  ids are stable, so logouts are not caused by vanished user ids.

### (4) 401 rate + cookie delivery
- `fetch_app_logs` (24h): `/api/auth/me` shows a **mix** of 401 and 200 (sample: 401≈11, 200≈6),
  plus `POST /api/push/subscribe` 401s. All client-facing traffic arrives via Cloudflare edge IPs
  (172.x). (`GET /health` 404 is unrelated app noise — app has no /health route.)
- HONEST CAVEAT: `/api/auth/me` returning 401 for anonymous/not-yet-logged-in visitors is EXPECTED.
  The 401 volume alone does NOT by itself prove unexpected logouts vs normal anonymous traffic. The
  diagnosis rests on config + the eliminations above.
- Cookie is **host-only** (no `Domain=`), `secure`, `samesite=lax`.
- `list_domains`: `talksme.in` verified, SSL active; `www.talksme.in` **verified=false**,
  `ssl_status=pending_validation`, `root_redirect_enabled=true`. `chat.talksme.in` (named by
  reporter) is **not attached to this deployment at all**.

## Root cause (most-supported)
Secret-regeneration, replica-secret-mismatch and DB-reseed are all **ruled out** by the evidence.
The recurring logouts are a **cookie-scoping / host-mismatch** problem:
- Session cookies are **host-only** (no `Domain`). A session created on one hostname is not sent on
  another. With apex `talksme.in` served, `www.talksme.in` still on `pending_validation`
  SSL + root_redirect, and `chat.talksme.in` not attached, any host the PWA loads/redirects to
  other than the apex drops the cookie → `/api/auth/me` 401 → "logged out".
- A `samesite=lax`, host-only cookie in an **installed PWA** (standalone context / service-worker
  storage partition) is prone to not being replayed on reopen → matches "logged out after reopening
  the PWA".
- Contributing one-time event: the 2026-10-27 secret change (if it touched JWT_SECRET) invalidated
  all pre-Oct-27 sessions once.

## Fixes
1. CODE (E1):
   a. Make `_boot()` SAFE: `reset_demo()` must never drop collections in production. Replace the
      "no superadmin ⇒ drop+reseed everything" trigger with an idempotent seed that only inserts
      missing seed users. (Latent catastrophic data-loss risk independent of the logout bug.)
   b. Set an explicit parent-domain cookie, `Domain=.talksme.in`, on both `omni_session` and
      `omni_customer`, so the session is shared across apex + www + subdomains instead of host-only.
      Re-evaluate samesite for the installed-PWA context.
2. USER (domain): Complete SSL validation/verification for `www.talksme.in`; attach the actual host
   the PWA runs on (e.g. `chat.talksme.in`) as a custom domain; ensure the PWA `start_url` uses one
   canonical verified host. Confirm whether JWT_SECRET was the secret changed on 2026-10-27.
3. USER (test/verify): In the PWA/browser DevTools capture a `Set-Cookie` on login and confirm it
   reaches the browser, its `Domain`, and which hostname the installed PWA actually loads.

## Not verified / limits
- Secret VALUES are never readable, so whether JWT_SECRET specifically changed on 2026-10-27 is
  UNVERIFIED. Live Set-Cookie headers and the PWA's actual host require browser/DevTools (user side).
