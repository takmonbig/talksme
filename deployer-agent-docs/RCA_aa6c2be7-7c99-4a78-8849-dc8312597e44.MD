## (3) Backend logs (last 24h, active run)
- **ZERO** lines matching `push failed`, `WebPushException`, `pywebpush` import error, `Traceback`, `ERROR`, or `Exception`. The "push" logger emits nothing — neither success nor failure.
- `POST /api/push/subscribe`: mostly **200 OK**; **4× 401 Unauthorized** (subscribe attempts with no/invalid auth — those never stored a subscription).
- `POST /api/conversations/*/messages`: **all 200 OK**. No 5xx anywhere. Overall status histogram for the window: 200 and a handful of 401 only.
- Significance: messages are being posted successfully and subscriptions exist, yet there is **no evidence any web-push send is attempted on message creation** — the send path logs nothing on either outcome. Either the send-on-new-message hook is not wired/invoked, or exceptions in lib/push.py are swallowed before the "push failed" logger line.

## (4) Replicas / in-process hub
- Tier_0 runs **2 replicas** (max_replicas=2, HPA disabled). CPU 50m/250m, mem 200Mi/512Mi.
- Per-pod uvicorn worker count is not visible from access logs (observed source IPs 172.69.x / 104.22.x are Cloudflare edge IPs, not backend pods).
- **The in-process WebSocket hub is therefore split across 2 independent pods.** A message POST landing on pod B cannot reach a WebSocket client connected to pod A (no shared broker / sticky routing), so in-app real-time delivery is inherently unreliable at 2 replicas. (Web-push itself reads subscriptions from shared Mongo, so replica count does not by itself break push — but it does break the in-memory hub.)

## Assessment
- Infrastructure side is clean: subscriptions stored, VAPID env present, message POSTs 200, no crashes/OOM, no push errors logged.
- The single strongest signal is the **total absence of any push-send logging** despite successful message posts — the web-push dispatch on new message appears not to execute or to fail silently before logging. This is a source/code question in the message-create → lib/push.py path, to be inspected by E1.
- Separately, the 2-replica in-process WebSocket hub is a real architectural limitation for real-time (non-push) delivery.
